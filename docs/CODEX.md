# Codex integration

RELAY starts a separate Codex App Server process over stdio for each member. It uses the supported App Server protocol rather than scraping a browser session or calling undocumented ChatGPT endpoints.

## Authentication and capability boundaries

- Each process receives a dedicated absolute CODEX_HOME directory. The host creates and secures that directory; the adapter requests file credential storage there. Treat the entire profile directory as sensitive.
- Login uses account/login/start with chatgpt or chatgptDeviceCode. The browser/device confirmation belongs to the user. The adapter never imports the desktop app's credentials and does not read auth.json.
- Forced ChatGPT login and an environment allowlist prevent inherited API-key or workload-identity settings from silently changing billing. RELAY does not bypass account limits or pool subscriptions.
- Capabilities are discovered from each process using skills/list and plugin/list. Only enabled skills and installed, enabled, unblocked plugins are reported as available. Plugin authentication and local configuration are separate from ChatGPT subscription login.
- File credentials are plaintext on disk, protected by filesystem permissions. They are neither encrypted by RELAY nor included in its frontend state. Users on a shared OS account are outside this isolation boundary.

See [official authentication documentation](https://learn.chatgpt.com/docs/auth) and [App Server documentation](https://learn.chatgpt.com/docs/app-server).

## Protocol details

The adapter was checked against the TypeScript protocol generated by the installed codex-cli 0.166.0-alpha.5.1, including experimental fields:

```powershell
codex app-server generate-ts --experimental --out .local/codex-protocol-experimental
```

The generated schema currently accepts sandbox "workspace-write" in thread/start and returns sandbox.type "workspaceWrite". RELAY requests approvalPolicy "on-request" and approvalsReviewer "user" and checks the returned policy before starting a turn. This protocol is versioned upstream and experimental room tool support can change; a future incompatibility should produce a visible error.

Initialize declares experimentalApi true. RELAY sends initialized once after the response. Every JSON message is one UTF-8 line; RPC responses are matched by ID and server-originated requests are distinct from notifications. Frames are limited to 8 MiB and pending requests to 128. Requests time out after 45 seconds. Invalid or oversized frames stop the process.

Register notification and request listeners before calling startTask. A fast turn/completed notification may arrive before the turn/start response, so the orchestrator must associate the in-flight member/task before awaiting the helper and must not overwrite a terminal task state afterwards.

## Room tools

Thread start includes two dynamic function definitions:

- relay_read_room with empty object arguments reads the current project/task room context.
- relay_report accepts kind (progress, blocker, handoff) and content text.

The server calls item/tool/call with threadId, turnId, callId, namespace, tool and arguments, and its own RPC id. The orchestrator validates the active task binding and handles the operation. A response must use that same id with:

```json
{ "contentItems": [{ "type": "inputText", "text": "Serialized result" }], "success": true }
```

Use dynamicToolResult(value, success) to construct the result. Room reports do not transfer ownership, grant filesystem access, merge code, or alter another task.

## Approval requests

Both item/commandExecution/requestApproval and item/fileChange/requestApproval accept a decision of accept or decline. RELAY must require the user to choose each approval; it must not convert approval into acceptForSession or install an execution/network policy amendment automatically.

Unsupported requests should receive client.rejectRequest(id), a JSON-RPC error with code -32601. Requests for new permissions, credentials, tools or forms must not be treated as generic execution approvals. The adapter declines unsupported requests automatically if no request handler is registered.

The turn/completed event contains threadId and turn with id, status, error, items and timing. Interpret completed, failed and interrupted distinctly. Streamed text and tool arguments are untrusted content.

## Shutdown and verification

The adapter starts hidden subprocesses without a shell. POSIX workers run in an owned process group; Windows shutdown terminates the owned PID tree with taskkill /T /F. The orchestrator must retain task locks if shutdown fails. Stderr is drained but never retained, and provider error messages are redacted before returning them.

Automated tests use a local fixture child process to check request correlation, credential environment isolation, actual protocol routing, active capability filtering, approval/sandbox policy checks, early completion events, malformed data and transport bounds. The actual installed CLI also completed an unauthenticated handshake and returned a null account in a fresh isolated profile. Live OAuth and billable model turns remain user tests; neither is implied by the fixture results.

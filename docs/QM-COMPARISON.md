# What Kivuno can learn from QM

Research note, 19 November 2026. I reviewed QM at `2884788`, Kivuno's `codex/shared-groups-sade` at `044ca7c`, and Kivuno's `main` at `1c0e168`. Both Kivuno branches identify as 0.8.5. The Shared Sade worker and tool-only paired-machine execution described below are on the development branch. [QM snapshot](https://github.com/yc-software/qm/tree/2884788ba107e1d19805cc07340cbee4ba7f4ff4) · [Kivuno development snapshot](https://github.com/dakiemdarktharr/WWW/tree/044ca7c457b0da746ab5d0998e96e4fcb5032b59) · [Kivuno main snapshot](https://github.com/dakiemdarktharr/WWW/tree/1c0e168c377fc01d97d1ade47ee550515554273c)

**Product recommendation.** Start with a small team shipping software on Windows and macOS. Let one developer ask for a fix, a second lend a machine to reproduce it, and a third review the change. Let the person merging inspect which version ran, which check passed on which machine, and whether the code about to land is still that version. Kivuno already implements much of the path between these people. The missing link is how a test result follows the change.

## How a QM request becomes work

1. A person writes in Slack or the web app. Core resolves the actor, participants, session and scope. A personal conversation, channel and project can have different memory, files and access. A scope is an authorization boundary as well as a place to store state. [QM overview and architecture](https://github.com/yc-software/qm/blob/2884788ba107e1d19805cc07340cbee4ba7f4ff4/README.md#architecture)
2. Postgres holds durable sessions and queued runs. A worker claims a run with a lease and heartbeats it. The orchestrator reconstructs the turn and supplies the selected model and QM tools to Pi. Model selection changes the model under that harness. Eligible turns can use the scope's sandbox to execute commands. Slack and web coordinator turns can delegate hands-on work to children. [Worker](https://github.com/yc-software/qm/blob/2884788ba107e1d19805cc07340cbee4ba7f4ff4/src/runs/worker.ts) · [Pi session creation](https://github.com/yc-software/qm/blob/2884788ba107e1d19805cc07340cbee4ba7f4ff4/src/agent/agent-run.ts#L408) · [Delegation rules](https://github.com/yc-software/qm/blob/2884788ba107e1d19805cc07340cbee4ba7f4ff4/docs/persistent-subagent-sessions.md)
3. For a swarm, the initiating session becomes the root. Each worker gets a durable session and a blank private computer. The swarm also has a shared board computer. An outbox records provisioning and notification work so a restart can resume it. Messages can wake another agent or wait in its mailbox. Workers using the shared disk coordinate their own concurrent writes. This is the clearest opening for Kivuno's Git ownership and integration rules. [Swarm design](https://github.com/yc-software/qm/blob/2884788ba107e1d19805cc07340cbee4ba7f4ff4/docs/swarms.md) · [Outbox implementation](https://github.com/yc-software/qm/blob/2884788ba107e1d19805cc07340cbee4ba7f4ff4/src/swarms/swarm-service.ts#L463)
4. Work can continue after the person leaves through scheduled jobs, watches and webhooks. Org configuration, scoped credentials, shareable skills and audience-aware memory make QM the stronger choice for an always-on internal assistant. It also has a live Mac-control tool for human-initiated desktop turns. Desktop access alone is a poor basis for distinguishing the two products. [QM features](https://github.com/yc-software/qm/blob/2884788ba107e1d19805cc07340cbee4ba7f4ff4/README.md#features) · [Desktop tool](https://github.com/yc-software/qm/blob/2884788ba107e1d19805cc07340cbee4ba7f4ff4/plugins/chassis/src/desktop-computer.ts)

## Where Kivuno has an advantage over QM

| Team need                                                  | What Kivuno can substantiate                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Keep using each member's actual coding agent               | Kivuno drives Codex App Server and Gemini CLI through ACP. On the Sade branch, Claude Code uses stream-JSON and Antigravity uses ACP under explicit managed-mode opt-in. Members keep provider logins on their own machines. QM's primary implementation gives its own Pi sessions model choice. Teams that rely on native harness behavior have a reason to choose Kivuno. [Codex](../server/codex.ts) · [Gemini](../server/gemini.ts) · [Managed providers and test limits](sade-managed-verification.vi.md)                                                                         |
| Protect a teammate's time and allowance                    | A Shared Sade grant binds one owner's harness and device to a project, expiry and turn budget. The group can admit a read-only contribution, and revoke access before a pending patch is delivered. The broker checks current membership and budget when assigning work. For a team lending access for one task, that is more specific than choosing a model for a swarm worker. [Grant checks](../server/group-sade.ts) · [Shared grant flow](shared-sade-verification.vi.md)                                                                                                         |
| Review once and deliver the reviewed code across checkouts | Shared Sade assigns patch review to another owner, binds approval to a diff digest and leaves integration with the machine owner. The dependent desktop checks the digest and file list before applying the patch to a private worktree. A no-change prerequisite can still block downstream work until the expected revision is in the receiving branch's history. Small reviewed changes can travel before a shared-remote push. [Group review](../server/group-sade.ts) · [Desktop import](../server/shared-sade-worker.ts) · [Cross-workspace tests](../tests/shared-sade.test.ts) |
| Borrow the machine that exhibits the bug                   | A grant can provide a tool-only runner. The provider stays on the initiating machine. The other computer supplies its OS, runs a command, and sends scoped changes back. Kivuno's recorded Windows → macOS arm64 run reproduced a path bug, observed exit 1 then exit 0, and returned one file. The AI side used a fixture. [Cross-host verification](shared-sade-verification.vi.md#chạy-lại-tình-huống-d-qua-mạng) · [Machine executor](../server/machine-execution.ts)                                                                                                              |

These advantages have limits. Shared Sade currently admits one active workflow per group or project and its automatic review requires complete text diffs of at most 12,000 characters. A worktree separates files during development. Process isolation still depends on the OS and runner. Teams that need large unattended jobs or organization-wide isolation have different requirements. [Review eligibility](../server/sade.ts) · [Admission and verification](shared-sade-verification.vi.md) · [Security model](SECURITY.md)

## Which novelty claims survive comparison?

| Closest alternative            | What its maintainers already document                                                                                                                                                                                                                                                                                                    | What Kivuno would have to demonstrate                                                                                                         |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Commonly                       | Multiple people bring their existing agents and workstations into a shared pod. [Commonly](https://commonly.me/)                                                                                                                                                                                                                         | A fix and its verification can pass between those owners with fewer manual interventions.                                                     |
| Hermesh                        | Device-signed grants and a demo where Claude fixes on Mac, Codex and Gemini check on Windows and Linux, and a failed check goes back for repair. [Hermesh](https://github.com/hermeshai/hermesh)                                                                                                                                         | A separately owned, tool-only machine can verify the precise reviewed input and a dependent task can consume that result under its own grant. |
| AgentLane                      | Exclusive path claims, independent review of a pushed commit against a specific base in a clean checkout, and an export of gate evidence. [AgentLane independent review](https://github.com/thetrueshags/AgentLane) · [Review workflow](https://github.com/thetrueshags/AgentLane/blob/main/docs/example.md#optional-independent-review) | Show the value of verifying across owners before a push, and demonstrate what happens after a target change, disconnect or revoked grant.     |
| Paradev and Agent Orchestrator | Worktree-based parallel CLI sessions, review and PR workflows are established. Agent Orchestrator also advertises support for over 35 coding agents. [Paradev](https://github.com/ParadevAI/Paradev#what-is-paradev) · [Agent Orchestrator](https://github.com/OrchestratorInc/agent-orchestrator)                                       | Beat the ordinary PR workflow on time or human effort for a specific workload. Adapter count is already a crowded metric.                     |

**Kivuno could let independent owners authorize, reproduce, review and hand off the same change before a push.** The evidence would follow the patch and expire when its inputs change. A head-to-head benchmark would show whether this saves the team time or catches defects that its usual workflow misses.

## Next developments, in order

1. **Bind one real check to the reviewed change.** Start with the existing paired-runner path and one project-approved command for the Windows/macOS fixture. Today the Shared Sade receipt stores the last platform, exit code and timeout, and includes them in summary text. Separately, the reviewer approves a hash of the file list and diff. Add an append-only runner result with the exact tested tree (including inherited patches), base/target revision, recipe and toolchain digest, command, runner identity and platform, grant reference, exit status and output digest. Capture the inputs at execution. On integration, compare against the candidate tree and current requirements. Surface pending, failed, passed and stale in Reviews. Provide a manifest that another authorized desktop can verify against a trusted runner identity. Existing optional AEGIS receipts can reference that manifest. A receipt authenticates what a trusted runner reported. The test itself determines what a pass establishes. [Current machine result and review check](../server/shared-sade-worker.ts) · [Diff digest](../server/sade.ts) · [AEGIS evidence boundary](AEGIS.md) · [SLSA provenance model](https://slsa.dev/spec/v1.2/provenance)
2. **Schedule only missing verification.** Let the owner declare requirements such as an independent code review and a macOS arm64 check. Sade should show eligible owners and runners, honor turn budgets and choose a tool-only run when the command is already known. A completed result can satisfy another dependency only when tested inputs, recipe, environment and access still match. Start conservatively with the full candidate tree. Narrowing invalidation to selected files requires a reliable dependency model. A failed or ambiguous command pauses the dependency and offers the evidence to the person handling the fix. [Existing grant and review scheduler](../server/group-sade.ts) · [Existing worker](../server/shared-sade-worker.ts)
3. **Prove the benefit with real people before adding more surfaces.** Recruit two owners with authenticated, different harnesses and one loaned Mac. Run the same cases with Kivuno and with a normal PR, CI and an independent human reviewer. Where possible, run the cross-machine case in Hermesh and the independent-landing case in AgentLane. Use identical repository revisions, seeded defects, check scripts, hardware class and model budgets. Counterbalance run order. Record setup time separately, then time to an accepted fix, manual handoffs, model turns, duplicate command executions, false accepts and false rejects. Publish failed trials alongside successful ones.

**Pilot decision.** Run at least five paired repetitions each for a cross-OS bug, a stale result after an edit, a disconnect after command completion, and revocation before handoff. Proposed engineering gates are zero stale acceptances, zero unauthorized deliveries and zero duplicate command executions after retry in that suite. Continue product investment if median hands-on coordination time falls at least 25% relative to PR + CI with equal or better acceptance accuracy. Report raw counts for this small sample. If the difference disappears after including setup, target teams with recurring access to special hardware before expanding to general-purpose teams.

**Evidence from this review.** On Windows with Node 24.22.1, all 30 tests across `shared-sade.test.ts`, `machine-execution.test.ts` and `handoffs.test.ts` passed. The 1,000-message case uses controlled planner outputs. QM's nine standalone skill-frontmatter tests also passed. I inspected QM's production paths in source and did not run its cloud stack. The prior Kivuno cross-host evidence uses real Windows and macOS with fixture harnesses. Its separate local Qwen review experiment caught 8 of 9 seeded defects and approved 6 of 9 correct patches. Real two-owner subscription performance and comparative benchmark results remain open.
